## 1. 项目概述

### 1.1 项目目标

构建一款 **跨平台（macOS + Windows）的本地 Markdown 编辑器与预览器**，核心体验是「所见即所得（WYSIWYG）」的编辑模式。

### 1.2 范围界定

**明确的「做」与「不做」：**

| 维度 | 范围 |
|------|------|
| ✅ 核心 | Markdown 文件的编辑、实时渲染、预览、导出 |
| ✅ 体验 | WYSIWYG 所见即所得、主题切换、快捷键、多标签页 |
| ❌ 明确不做 | 登录 / 注册 / 账户体系 |
| ❌ 明确不做 | 云同步 / 云端存储 / 多端同步 |
| ❌ 明确不做 | 服务端 / 后端 / 数据库 |
| ❌ 明确不做 | 账户验证 / 授权 / 订阅付费 |

> 结论：这是一个**纯本地单机应用**，不依赖任何服务端。所有数据保存在用户本地磁盘，无网络请求（不做自动更新）。

### 1.3 成功标准（MVP 验收）

- 在 macOS 与 Windows 上均能安装、启动、正常编辑 `.md` 文件
- 输入 Markdown 语法时，光标所在行即时渲染为对应样式（WYSIWYG）
- 支持标题、列表、表格、代码块、引用、链接、图片、任务列表等常用语法
- 提供多套主题（含深色主题）与源码/渲染视图切换
- 文件打开、保存、拖拽打开、最近文件等基础能力完善
- 应用启动冷启动时间 < 3 秒，大文件（1 万行）编辑不卡顿

## 2. 架构范式参考

> 本节说明项目的架构取向：为什么采用「壳 + Web 渲染」而不是原生 UI 自绘。
> 结论来自同类 Markdown 编辑器的公开资料与社区实践归纳，不涉及任何私有代码或资源。

### 2.1 主流做法：壳 + Web 渲染

成熟的 Markdown 编辑器普遍采用「原生壳 + Web 渲染引擎」的混合架构：

```
┌─────────────────────────────────────────────┐
│              原生壳（Native Shell）           │
│   窗口 / 菜单 / 文件系统 / 系统集成           │
│  ┌───────────────────────────────────────┐  │
│  │           内嵌 WebView（Web 渲染）     │  │
│  │  index.html + CSS + JS                │  │
│  │  ├─ 编辑内核（可编辑 DOM + 事务）      │  │
│  │  ├─ Markdown 解析与序列化              │  │
│  │  ├─ 公式 / 图表 / 语法高亮             │  │
│  │  └─ 主题 CSS                          │  │
│  └───────────────────────────────────────┘  │
│        ▲  JS ↔ 原生 双向消息桥接             │
└─────────────────────────────────────────────┘
```

这样分工的好处：排版能力直接复用 Web 生态（CSS 排版、公式、图表、语法高亮），
跨平台表现一致；壳只负责系统能力，职责清晰。

### 2.2 对本项目的指导

1. **WYSIWYG 的本质**：在可编辑的 DOM 中隐藏或样式化 Markdown 标记符号，同时维护一份源码映射。这是本项目最核心、最难的部分。
2. **Electron 天然就是「壳 + Web」**：无需自研原生壳，直接复用该范式，把精力放在编辑体验上。
3. **渲染依赖优先选成熟开源库**：公式、图表、高亮、解析各有事实标准，站在生态上比自己造轮子稳。
4. **范围克制**：账户体系、云同步、自动更新一律不做，保持纯本地单机定位。

### 2.3 自主实现原则

本项目全部基于开源库自主实现，不复制、不引用任何商业软件的私有代码、资源文件或品牌标识。

## 3. 技术选型

### 3.1 核心技术栈

| 层 | 选型 | 理由 |
|----|------|------|
| **应用框架** | **Electron** | 天然「原生壳 + Web 渲染」架构；跨平台一致性强；生态最成熟；VS Code 同款方案 |
| **语言** | TypeScript | 类型安全，大型编辑器项目必备，重构与协作友好 |
| **前端框架** | React 18 | 组件化、生态大、与编辑器库集成方案多 |
| **构建工具** | Vite + electron-builder | 开发热更新快；electron-builder 成熟支持双平台打包 |
| **包管理** | npm workspaces | 原生支持 Monorepo，无需额外工具；与 Electron 生态兼容性好 |

### 3.2 关键依赖库

| 能力 | 选型 | 说明 |
|------|------|------|
| **WYSIWYG 编辑内核** | **Milkdown** 或 **ProseMirror**（见 3.3 专门对比） | 所见即所得的核心 |
| **数学公式** | **KaTeX**（首选）/ MathJax 4 | 渲染快；KaTeX 体积更小更快 |
| **图表** | **Mermaid** + **ZenUML** | 生态成熟，覆盖流程图/时序图等常用图种 |
| **代码高亮** | **Shiki**（首选）/ highlight.js | Shiki 用 VSCode 同款高亮，质量更高 |
| **文件搜索** | **ripgrep**（`@vscode/ripgrep` 或直接调用） | 性能最优，VS Code 同款；0.14.0 已提供基于 Node 扫描的侧栏文件夹搜索（中小目录够用），ripgrep 版本计划 v1.2 引入 |
| **Markdown 解析** | **remark** / **markdown-it** | 用于导出/预览管线 |
| **序列化** | **remark** + 自定义 serializer | 源码 ↔ DOM 互转 |

### 3.3 WYSIWYG 编辑器内核选型（重点决策）

这是本项目的核心决策，单独说明。

| 方案 | 原理 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| **A. Milkdown** | 基于 ProseMirror + remark，插件式 Markdown 编辑器框架 | 开箱即用；插件生态成熟；输入即 Markdown；源码↔WYSIWYG 双模式原生支持 | 相对较新，深度定制需理解其插件体系 | ⭐ **首选** |
| **B. 直接用 ProseMirror** | 底层编辑框架，需自行搭建 Markdown schema + 序列化 | 最灵活、可控性最高；可实现深度定制 | 开发量大，需自己写 schema/命令/序列化 | 备选（若 Milkdown 定制受限时降级） |
| **C. CodeMirror 6 + 装饰器模拟 WYSIWYG** | 用 CM6 的 decoration 隐藏语法符号、叠加样式 | 性能极佳、光标行为精确 | 实现「所见即所得」需要大量装饰器工作，且复杂块级元素（表格/嵌套列表）难做到位 | 不推荐用于 WYSIWYG，但源码模式可用 |

> **决策**：MVP 采用 **Milkdown**（方案 A），它本质就是 ProseMirror + remark 的 Markdown 专用封装，兼顾了开发效率与生产级的 WYSIWYG 能力。若后续发现 Milkdown 无法满足某个深度定制点，再局部下沉到 ProseMirror（方案 B）直接操作，两者技术栈同源，迁移成本低。

### 3.4 为什么不用 Tauri（对比说明）

| 维度 | Electron | Tauri |
|------|----------|-------|
| 渲染一致性 | Chromium 固定版本，双端一致 | 依赖系统 WebView（macOS=Safari/WebKit，Windows=WebView2），渲染差异需逐个适配 |
| 编辑器生态兼容 | Milkdown/ProseMirror 等均在 Chromium 上充分测试 | WebKit/WebView2 对部分 CSS/JS 特性支持不一，WYSIWYG 编辑器风险高 |
| 内存/体积 | 较大（约 100MB+） | 小（约 10MB+） |
| 开发门槛 | 纯前端，低 | 需 Rust 基础 |

> 对于「WYSIWYG 编辑器」这种对渲染一致性要求极高的应用，**Electron 的 Chromium 固定版本是明确优势**，牺牲体积换稳定性是值得的。故最终选 Electron。

### 4.1 分层架构

```

│                    应用层 (App Layer)                    │
│   窗口管理 / 菜单 / 快捷键 / 托盘 / 最近文件 / 主题管理    │
├────────────────────────────────────────────────────────┤
│                    渲染层 (Renderer)                     │
│   ┌──────────────┐  ┌──────────────┐  ┌──────────────┐ │
│   │  编辑器视图    │  │   侧边栏      │  │  状态栏/UI    │ │
│   │  (Milkdown)   │  │ (大纲/文件树) │  │  (React)     │ │
│   └──────────────┘  └──────────────┘  └──────────────┘ │
├────────────────────────────────────────────────────────┤
│               核心领域层 (Core / Domain)                  │
│   Markdown 解析 / 序列化 / 大纲生成 / 搜索 / 导出          │
├────────────────────────────────────────────────────────┤
│                 IPC 桥接层 (ipcMain/ipcRenderer)         │
├────────────────────────────────────────────────────────┤
│               主进程服务层 (Main Process)                 │
│   文件读写 / 目录监听 / 剪贴板图片 / 系统对话框 / ripgrep   │
├────────────────────────────────────────────────────────┤
│               操作系统 (macOS / Windows)                 │
└────────────────────────────────────────────────────────┘
```

### 4.2 进程模型（Electron 标准三进程）

| 进程 | 职责 | 说明 |
|------|------|------|
| **主进程 (Main)** | 窗口生命周期、文件 I/O、原生 API、菜单、托盘、IPC 路由 | 仅一个 |
| **渲染进程 (Renderer)** | 编辑器 UI、渲染、交互 | 每个窗口一个，启用 `contextIsolation` + `sandbox` |
| **Utility/GPU 进程** | 由 Chromium 自动管理 | 无需干预 |

### 4.3 安全基线（Electron 必做）

- 开启 `contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`
- 渲染进程禁用 `remote`，所有原生能力通过 `contextBridge` 暴露的白名单 API
- 加载本地资源仅用 `file://` 或自定义协议，**不加载任何远程内容**
- `CSP` 限制 `script-src 'self'`，禁止内联远程脚本；并保持 `object-src 'none'` / `base-uri 'self'` / `form-action 'none'`
- `img-src` 额外放行 `file:`（本地文档图片按绝对路径加载），不放行 `http(s)`
- 图片等本地资源用 `webSecurity` 保持默认开启

### 4.4 数据流（编辑链路）

```
用户输入
   │
   ▼
Milkdown 编辑器（ProseMirror 状态）
   │  transaction 变更
   ▼
ProseMirror Doc (结构化 AST)
   │
   ├──▶ 实时渲染到 DOM（WYSIWYG）
   │
   └──▶ remark serializer ──▶ Markdown 文本
                                   │
                                   ▼
                         主进程写盘（防抖保存）
                                   │
                                   ▼
                         大纲/字数统计/预览导出
```

## 6. WYSIWYG 编辑器实现方案

### 6.1 核心机制：语法符号的「隐藏与显现」

WYSIWYG 的本质是：**当光标不在某一行时，该行的 Markdown 语法符号（如 `#`、`*`、`**`）被 CSS 隐藏或样式化，只显示渲染效果；当光标移入该行时，语法符号重新显现以便编辑。**

在 Milkdown/ProseMirror 中的实现方式：

1. **AST 是唯一数据源**：Milkdown 内部用 ProseMirror 的 `Doc` 节点树，每个 Markdown 结构（标题、加粗、列表）对应一个 schema 节点，语法符号**不进入 DOM**（由插件在序列化时生成）。
2. **光标感知**：通过 ProseMirror 的 `Selection` 状态，判断光标当前所在节点。
3. **Mark 与装饰**：对「光标所在节点的语法符号」用 ProseMirror `Decoration` 渲染出临时的可见符号（如显示 `#`），非焦点区域则保持纯渲染样式。

### 6.2 关键交互能力清单

| 能力 | 实现要点 |
|------|----------|
| 输入 `#` + 空格 → 标题 | 监听输入，触发 Markdown 命令转换 |
| 输入 `- ` → 无序列表 | 同上，自动进入列表 |
| 输入 `**文本**` → 加粗 | Mark 的闭合触发 |
| 表格创建与行列编辑 | 工具栏 / 斜杠菜单都用 8 列 × 6 行的行列网格选规模（点哪格插几行几列，`insertTable` 带 `列x行` payload，缺省才退回 3×3；源码模式同一套 payload）；table 节点用自定义 NodeView 包一层，列头与行首渲染选择手柄（默认隐藏，悬停表格 / 光标在表内 / 有整格选区时浮现），左上角角手柄点击选中整张表（圆角只给角手柄，紧邻的第一列 / 第一行手柄保持直角，否则实色手柄带交界处会露白缺口）；点选整行 / 整列后浮出增删工具条（前插 / 后插 / 删除行列 / 删除整表），命令统一走 `format` 分发 |
| 表格选择坐标 | `CellSelection.colSelection/rowSelection` 需要「单元格节点前」的 ResolvedPos（`$cell.node(-1)` 必须是 table）；单元格内还有一层 paragraph，多进一层会抛 `Not a table node`。命令后收回普通文本光标，避免整格选区下一次输入清空整行 / 整列 |
| 代码块 + 语言高亮 | 代码块节点视图 + Shiki |
| 数学公式（行内/块级） | `$...$` / `$$...$$` + KaTeX（**v1.1 引入**） |
| 图表（mermaid） | 围栏代码块 ` ```mermaid ` + Mermaid 渲染 |
| 任务列表 `- [ ]` | checkbox 自定义节点 |
| 图片粘贴/拖拽 | 主进程写入本地，渲染进程插入 |
| 底部工具栏 / 快速插入菜单 / 原生菜单统一入口 | 三处共用格式化入口；链接走「文本 + 地址」表单（菜单快捷键复用工具栏表单），图片走系统文件选择器，任何入口都不插占位语法。代码块在工具栏只保留一个按钮（空选区点击即转成可见代码块），段落下拉只放正文与标题；行内代码只走原生菜单，空选区用 `toggleMark` 的 storedMark 处理，避免预设命令返回 false 导致点击无反应 |
| 警告框插入 | 统一发 `insertCallout` + 类型；片段插入后在新区间选中「内容」占位文字，用户直接输入即替换，保证 `[!NOTE]` 始终是引用块首行文本、装饰不失效（工具栏另有 5 种类型下拉） |
| 大纲拖动重排章节 | `OutlineList.tsx` 负责 HTML5 拖放与落点指示，`shared/text.ts` 的 `moveOutlineSection` 纯按行搬运：章节范围取「下一个层级不高于当前标题的行」之前，连子标题与正文整体移动；拖动前同步编辑器回写并重新解析大纲 |
| 任务列表空项回车 | 空任务项再回车退出列表，光标落到列表后的正文段落（事务后置插件补回焦点） |
| 链接自动识别与跳转 | 点击 + Cmd/Ctrl 跳转 |
| **中文输入法（IME）适配** | 见 6.4 节（**已确定：需专项适配**） |

### 6.3 中文输入法（IME）适配方案

中文拼音/五笔等输入法使用「组合输入（Composition）」机制，与 WYSIWYG 的「输入即转换」存在天然冲突：组合中的拼音字母不应触发 Markdown 语法转换。需专项处理：

| 场景 | 问题 | 处理方案 |
|------|------|----------|
| 拼音组合中 | 组合中的字母被误判为 Markdown 符号（如 `#`、`*`） | 监听 `compositionstart` / `compositionend`，组合期间**暂停所有 Markdown 自动转换** |
| 候选词上屏 | 上屏时触发多余的事务 | 仅在 `compositionend` 后统一应用一次事务 |
| 半角/全角符号 | 中文输入法切换全角符号 | 对全角符号做归一化判断（可选，低优先级） |
| 光标与装饰符 | 组合期间装饰符位置错乱 | 组合期间冻结 decoration 重算 |

> **实现要点**：在 Milkdown 的 input 规则与键盘事件处理中，增加一个「IME 组合状态守卫」。ProseMirror 已内置 `compositionstart/end` 事件支持，但需在自定义 Markdown 转换命令处显式跳过组合状态。这是国内用户体验的关键点，M1 阶段即需纳入，而非事后修补。

### 6.4 大文档性能策略

- **延迟派生计算（已落地）**：大纲提取走 React `useDeferredValue`，连续输入只解析最后一次；查找栏未打开时不计算全文纯文本。低频但要求精确的操作（大纲拖动重排）不能直接用延迟值，须先同步编辑器回写、再按最新源码重新解析一次
- **虚拟化渲染**：仅渲染可视区域 + 缓冲区（Milkdown 社区有成熟方案，或 ProseMirror 的 `Decoration` 惰性计算）
- **防抖持久化（已落地）**：内容变化后 1.5s 防抖写盘，覆盖所有已落盘标签
- **打开体积上限（已落地）**：超过 20 MB 或二进制内容直接拒绝打开，避免误拖大文件把主进程读满
- **分块解析**：超大文件（> 5MB）降级为「纯文本模式 + 折叠预览」（未实现）
- **Math/图表懒渲染**：非可视区域的公式与图表延迟渲染（Mermaid/KaTeX 已由插件按需渲染，未做可视区域裁剪）
- **启动分块（已落地）**：编辑器内核（Milkdown + Shiki + Mermaid + KaTeX）动态 `import`，入口 chunk 从 3.18 MB 降到约 0.59 MB；
  菜单重建前比较状态签名、菜单分发表只构造一次，避免近百个闭包与整棵菜单的高频重建

## 7. Markdown 解析与渲染管线

### 7.1 双管线设计

| 管线 | 用途 | 技术 |
|------|------|------|
| **编辑管线** | WYSIWYG 编辑，AST 即 ProseMirror Doc | Milkdown（内部 remark 解析） |
| **导出/预览管线** | 生成 HTML/PDF、纯预览 | remark-rehype → HTML |

两条管线**共享同一套 remark 插件**（GFM、脚注、数学、表格等），保证编辑所见与导出结果一致。

### 7.2 支持的语法范围

- **块级**：标题（1-6）、段落、引用、有序/无序列表、任务列表、表格、代码块、分割线、脚注、数学块（v1.1）
- **行内**：加粗、斜体、删除线、行内代码、链接、图片、行内数学（v1.1）、高亮标记、上下标
- **扩展**：GFM（GitHub Flavored Markdown）、目录 TOC、YAML front matter（可选）
- **图表**：Mermaid（流程图/时序图/甘特图/类图等）、ZenUML 时序图

### 7.3 导出

| 目标格式 | 实现 |
|----------|------|
| HTML | marked + 主题 CSS 内联；数学公式经 `mathExport.ts` 用 KaTeX 渲染并内联 CSS/woff2 字体（data URI，仅含公式的文档才嵌入） |
| PDF | 复用 HTML（含公式渲染）+ Electron `webContents.printToPDF`（隐藏窗口加载临时文件） |
| Word | Word 可打开的 HTML（.doc）；KaTeX HTML 无法在 Word 渲染，公式保留 TeX 原文 |
| 图片 | 可选（HTML → 截图，低优先级） |

> 公式导出管线：`extractMath`（块级 `$$...$$` 先于行内 `$...$`；围栏代码块与行内代码掩码保护）
> → marked 渲染 → `restoreMath`（`katex.renderToString`，`throwOnError:false` 失败渲染为错误标记）。
> 货币文本（如 `$5, $10`）因「首尾非空白」约束不会被误判。

## 8. 文件管理

### 8.1 职责划分

- **主进程**负责所有文件 I/O（读写、监听、最近文件记录）。
- **渲染进程**通过 IPC 调用，不直接碰文件系统（安全基线要求）。

### 8.2 关键能力

| 能力 | 实现 |
|------|------|
| 打开文件 | 系统对话框 / 拖拽 / 命令行参数；打开前 `stat` 校验体积（≤ 20 MB）与二进制内容 |
| 保存 | 防抖自动保存（1.5s，覆盖所有已落盘标签）+ `Cmd/Ctrl+S` 手动保存；保存统一写 UTF-8 |
| 原子写入 | `main/fileWrite.ts` `writeFileAtomic`：同目录临时文件 → `fsync` → `rename` 替换（保留原权限位，Windows 被占用时退回直接覆盖）；崩溃/断电不会留下截断文档 |
| 自动保存 | 写盘前比对各文件「本应用最后一次读到/写成功」的 mtime + size（`recordDiskStamp`），被外部改过就抛 `EXTERNAL_CHANGED` 并暂停该标签的自动保存；失败写入状态栏（`saveState`），不静默吞掉 |
| 关闭标签 | 有路径且 dirty 时 `await` 写盘成功才移除标签；失败保留标签与脏点并在状态栏说明原因 |
| 外部修改监听 | 当前活动文档 `fs.watch`（250ms 去抖、自身写入 1.5s 宽限）；无未保存改动可「重新加载」，有改动则暂停自动保存并提供「载入磁盘版本」 |
| 关闭确认 | 主进程在窗口 `close` 时询问未保存汇总；确认后发带 `requestId` 的 `app:flush-before-close`，等 `app:flush-reply` 回包（15s 超时；失败清单逐条列出）才真正关闭 |
| 最近文件 | 主进程持久化 JSON（`userData/recent.json`） |
| 编码识别 | BOM（UTF-8 / UTF-16LE / UTF-16BE）→ 严格 UTF-8 → GBK；保存统一转 UTF-8（带 BOM 保留 BOM），状态栏显示当前编码 |
| 换行符 | 尊重文件原有 CRLF/LF（读取原样、写回原样） |
| 图片粘贴 | **存到文档同级的 `img/` 目录**（引用 `img/xxx.png` 相对路径） |

> **图片粘贴存储策略（已确定）**：粘贴/选择的图片保存到当前文档同级目录下的 `img/` 文件夹，Markdown 中使用相对路径 `![name](img/xxx.png)` 引用。保证文档可移植（文档 + `img/` 目录整体拷走即可用）、避免 `.md` 文件体积膨胀。未保存的新文档会先提示另存为，再落盘图片。

### 8.3 配置存储

- 应用配置 → 主进程 `userData/settings.json`（自研 JSON 读写，不额外引入依赖）。
- **已实现**：主题、侧栏开关与面板、标签栏/工具栏可见性、缩放百分比、窗口尺寸与位置、会话恢复开关与上次打开的标签路径。
- 会话恢复只保存路径、不保存未落盘内容：未落盘文档由「关闭前确认」负责，避免设置文件变成隐式草稿箱。
  主进程启动时读入内存、写入按 300ms 防抖，退出前强制落盘；渲染层启动后通过 IPC 拉取并应用。
- 读取时会做字段校验，损坏或越界的值自动回落到默认值；窗口位置若已不在任何屏幕内则回到默认尺寸。

## 9. 主题系统

### 9.1 设计（主题即一份 CSS）

- **主题 = 一组 design tokens → CSS 变量**，颜色/字体/间距全部走变量，明暗切换只改变量值。
- 已实现两套主题：
  - `light`（明亮，默认）
  - `dark`（深色）

- 待做：第三套主题（如 GitHub 风格）、用户自定义主题目录（`userData/themes/`）。

### 9.2 CSS 变量规范（示例）

```css
:root {
  --md-font-size: 16px;
  --md-line-height: 1.6;
  --md-text-color: #333;
  --md-bg-color: #fff;
  --md-heading-color: #000;
  --md-link-color: #4183c4;

```

编辑器与预览/导出共用同一套变量，保证「编辑所见 = 导出所得」。

## 10. 跨平台构建与分发

### 10.1 构建配置

| 平台 | 打包工具 | 产物 | 出包位置 |
|------|----------|------|----------|
| macOS arm64 | electron-builder + 本地镜像脚本 | `.dmg`（安装窗口：应用 / 箭头 / Applications） | 本机或 arm64 CI job（默认） |
| Windows x64 | electron-builder | `.exe`（NSIS 安装包） | Windows CI job（默认） |
| macOS x64 | electron-builder | `.dmg` | 仅手动触发 CI 且选 `all` 时产出 |

架构由命令行 `--arm64` / `--x64` 指定，不做 universal；`mac.artifactName` 必须带 `${arch}`，否则两个架构的产物互相覆盖。

CI 的打包目标由 `workflow_dispatch` 的 `targets` 选项决定（`default` = macOS arm64 + Windows x64、`mac-arm64`、`win-x64`、`all` 含 macOS x64），`v*` tag 触发时按 `default` 走；矩阵由 `plan` job 生成后传给 build job，想临时出 Intel 包只需手动跑一次 `targets=all`，不用改文件。

版本号与 tag 的对应关系由 `scripts/check-release-version.mjs` 守住：`plan` job 在 tag 触发时先跑一次，比对 `GITHUB_REF_NAME` 去掉 `v` 后是否等于 `package.json` 的 `version`，同时校验 5 处版本号（两个 `package.json` + `package-lock.json` 的 `version` / `packages[""]` / `packages["apps/desktop"]`）彼此一致。`plan` 是 `build` 的 `needs`，不一致即整个打包阶段跳过——避免出现「Release 标签 1.0.1、附件却叫 1.0.0」的错位发布。安装包名里的 `${version}` 与 `Info.plist` 的版本都由 `package.json` 派生，tag 是另一条独立输入，二者必须显式对齐。

### 10.2 关键配置（`apps/desktop/electron-builder.json`）

```json
{
  "appId": "com.markdownnote.app",
  "productName": "MarkdownNote",
  "npmRebuild": false,
  "files": ["out/**/*", "package.json"],
  "mac": {
    "target": ["dmg"],
    "artifactName": "${productName}-${version}-${arch}.${ext}"
  },
  "win": { "target": ["nsis"] }
}
```

- 配置文件必须是官方识别的 `electron-builder.json`（`.ts` 版在 Windows runner 有盘符问题）。
- 纯本地应用固定 `npmRebuild: false`：CI 若重装依赖会删掉打包所需的二进制文件。
- main / preload 用 `externalizeDepsPlugin({ exclude: ['@ai-md-editor/shared'] })` 内联 workspace 包。
- 构建前清空 `out/`：渲染层不自动清目录，历史 `index-<hash>.js` 会被一并打进 `app.asar`（实测 415M → 21M，dmg 271M → 159M）。

### 10.3 平台差异处理

| 差异点 | macOS | Windows |
|--------|-------|---------|
| 菜单栏 | 应用顶部全局菜单 | 窗口内菜单 |
| 快捷键修饰键 | `Cmd` | `Ctrl` |
| 文件关联 | `Info.plist` / `CFBundleDocumentTypes` | 注册表 / NSIS |
| 自动更新 | 不做（**已确定**：MVP 及后续均手动分发） | 不做 |
| 字体 | 系统 SF Pro / PingFang | Segoe UI / 微软雅黑 |
| 换行与路径 | `/` | `\`（统一用 `path` 模块处理） |

### 10.4 签名与分发现状

- macOS 本地包：`codesign --force --deep --sign -` 的 ad-hoc 签名（Apple Silicon 必需，完全未签名会被系统拒绝启动），未做公证；首次打开需在访达中右键→打开。正式签名 + 公证仍属后续项。
- Windows：代码签名证书可选，当前不签。
- 常态分发靠 CI：推 `main` 或打 `v*` tag 产出三架构，打 tag 时自动创建 Release 并上传产物。账号计费导致 workflow 被阻断时按 10.5 本地出包，期间只推 `main`、不打 tag。

### 10.5 本地出包（CI 不可用时的替代路径）

```bash
npm run build                       # out/ 必须干净
cd apps/desktop
env -u NODE_OPTIONS -u ELECTRON_RUN_AS_NODE CSC_IDENTITY_DISABLED=1 \
  ../../node_modules/.bin/electron-builder --mac --arm64 --dir
cd ../..
bash scripts/make-dmg.sh <版本号> arm64
```

- **为什么分两步**：受限环境里 dmg target 内部 `ditto` 会在挂载卷留下 `.BC.T_*` 临时文件，删除动作被拦截后报 `ERR_ELECTRON_BUILDER_CANNOT_EXECUTE`；`--dir` 只产 `.app`，镜像由脚本用 HFS+ 可写镜像 + `COPYFILE_DISABLE=1 ditto --norsrc --noextattr --noacl` 组装，再 `hdiutil convert -format UDZO` 压缩。
- **安装窗口**：卷挂到 `/Volumes/<卷名>` 才能写 `.DS_Store` 布局与自定义卷图标；窗口 540×348、96px 图标，应用 (140,140) / 箭头 (270,140) / Applications (400,140)；箭头用「文件名为单个空格 + `sips -i` 自定义图标」实现，避免缩略图白底与文件名标签；新版 Finder 不显示 `.DS_Store` 背景图，不要再往背景图方向做。
- **交付校验**：`hdiutil verify`（校验和有效）、卷内条目齐全、`codesign -dv` 为 `Signature=adhoc`、`Info.plist` 版本号一致、`lipo -archs` 为 arm64、`app.asar` 内 main / preload / renderer 文件与 `out/` 逐字节比对（确认改动确实进包）。

## 12. 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| **WYSIWYG 复杂度高** | 核心体验难达标，开发周期长 | 用 Milkdown 降低门槛；先覆盖 80% 的高频语法；必要时下沉 ProseMirror |
| **Milkdown 深度定制受限** | 某些细节无法与成熟产品完全一致 | 明确「自研实现、不追求像素级复刻」；受限点局部用 ProseMirror 插件补 |
| **大文件性能** | 万行文件卡顿 | 虚拟化渲染 + 分块解析 + 超限降级纯文本 |
| **跨平台渲染差异** | Windows 字体/DPI 显示差异 | Electron 固定 Chromium 已大幅消除；字体用 fallback 链；DPI 用 `devicePixelRatio` 适配 |
| **图片粘贴的存储策略** | 图片路径引用混乱 | 已确定：统一存到文档同级 `img/` 目录，Markdown 用相对路径（见 8.2 节） |
| **Electron 包体积大** | 分发体积约 100MB+ | 接受；后续可评估精简依赖与资源裁剪 |
