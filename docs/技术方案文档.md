## 1. 项目概述

### 1.1 项目目标

构建一款 **跨平台（macOS + Windows）的本地 Markdown 编辑器与预览器**，核心体验对标 Typora，聚焦「所见即所得（WYSIWYG）」的编辑模式。

### 1.2 范围界定

**明确的「做」与「不做」：**

| 维度 | 范围 |
|------|------|
| ✅ 核心 | Markdown 文件的编辑、实时渲染、预览、导出 |
| ✅ 体验 | WYSIWYG 所见即所得、主题切换、快捷键、多标签页 |
| ❌ 明确不做 | 登录 / 注册 / 账户体系 |
| ❌ 明确不做 | 云同步 / 云端存储 / 多端同步 |
| ❌ 明确不做 | 服务端 / 后端 / 数据库 |
| ❌ 明确不做 | 账户验证 / 授权 / 订阅付费 |

> 结论：这是一个**纯本地单机应用**，不依赖任何服务端。所有数据保存在用户本地磁盘，无网络请求（不做自动更新）。

### 1.3 成功标准（MVP 验收）

- 在 macOS 与 Windows 上均能安装、启动、正常编辑 `.md` 文件
- 输入 Markdown 语法时，光标所在行即时渲染为对应样式（WYSIWYG）
- 支持标题、列表、表格、代码块、引用、链接、图片、任务列表等常用语法
- 提供多套主题（含深色主题）与源码/渲染视图切换
- 文件打开、保存、拖拽打开、最近文件等基础能力完善
- 应用启动冷启动时间 < 3 秒，大文件（1 万行）编辑不卡顿

## 2. Typora 逆向分析结论

> 基于 `Typora.dmg`（版本 1.14.15，Build 7789）的静态逆向分析。分析手段：解包 `.app` 结构、读取 `Info.plist`、`Podfile`、依赖库清单、渲染引擎资源目录 `TypeMark` 及 JS 桥接代码。

### 2.1 架构总览

Typora 的架构可以概括为：**「原生壳（Objective-C/Swift）+ Web 渲染引擎（HTML/CSS/JS）」的混合架构**。

```
┌─────────────────────────────────────────────────────┐
│                   原生壳 (Native Shell)               │
│  Objective-C / Swift + Cocoa (AppKit)               │
│  ┌───────────────────────────────────────────────┐  │
│  │              WKWebView (WebKit)               │  │
│  │  ┌─────────────────────────────────────────┐  │  │
│  │  │         TypeMark 渲染引擎 (Web)          │  │  │
│  │  │   index.html + CSS + JS                 │  │  │
│  │  │   ├─ CodeMirror (编辑)                  │  │  │
│  │  │   ├─ 自定义 Markdown 渲染器              │  │  │
│  │  │   ├─ MathJax4 (数学公式)                │  │  │
│  │  │   ├─ Mermaid (图表)                     │  │  │
│  │  │   └─ 主题 CSS                            │  │  │
│  │  └─────────────────────────────────────────┘  │  │
│  └───────────────────────────────────────────────┘  │
│          ▲ WebViewJavascriptBridge 双向通信          │
└─────────────────────────────────────────────────────┘
```

### 2.2 关键逆向发现（事实依据）

| 发现项 | 逆向证据 | 结论 |
|--------|----------|------|
| **原生技术栈** | `Podfile` 引用 CocoaPods、`platform :osx, '12.0'`、主二进制为 Mach-O universal（arm64 + x86_64）、`DTCompiler` 为 clang | macOS 端为 Objective-C/Swift 原生开发 |
| **渲染引擎是 Web** | `Resources/TypeMark/` 下含 `index.html`、`style/`、`lib/`（JS/CSS 资源） | 编辑器 UI 与渲染全部用 Web 技术实现 |
| **用 WebKit 非 Chromium** | 主二进制 `otool -L` 链接 `WebKit.framework`、`WebViewJavascriptBridge` 代码、`window.webkit.messageHandlers` | 原生 WKWebView 承载渲染 |
| **WYSIWYG 编辑内核** | `lib/codemirror/mode.min.js` | 基于 CodeMirror 的编辑内核做所见即所得 |
| **数学公式** | `lib/MathJax4/` | 用 MathJax 4 渲染 LaTeX 公式 |
| **图表** | `lib/diagram/mermaid.min.js`、`mermaid-zenuml.min.js` | Mermaid + ZenUML 渲染流程图/时序图 |
| **全文搜索** | `lib/bin/{arm,x64}/rg`（ripgrep 二进制，分平台架构） | 用 Rust 的 ripgrep 做文件搜索 |
| **自动更新** | `Sparkle.framework` + `SUFeedURL` | Sparkle 做 macOS 自动更新 |
| **云同步（不做）** | `lib/aws-sdk.min.js`、`NSAppTransportSecurity` 放开 | 通过 AWS SDK 做云同步，本项目明确排除 |
| **主题系统** | `style/themes/` 下 6 套 CSS（github/gothic/newsprint/night/pixyll/whitey） | 主题 = 一份 CSS 文件，可扩展 |
| **原生桥接** | `window.bridge`、`WebViewJavascriptBridge`、`registerHandler/callHandler` | JS ↔ 原生通过消息桥接通信 |

### 2.3 对本文档的指导意义

1. **WYSIWYG 的本质** = 在可编辑的 DOM 中，把 Markdown 标记符号隐藏/样式化，同时维护一份隐藏的源码映射。这是本项目最核心、最难的部分。
2. **「原生壳 + Web 渲染」是成熟范式**：Typora 证明这种混合架构在性能和体验上完全可行。对本项目而言，**Electron 天然就是「壳 + Web」**，无需再手写原生壳，直接复用这一范式。
3. **依赖选型可直接对齐**：CodeMirror / MathJax / Mermaid 都是成熟开源库，本项目可直接采用对应生态。
4. **排除项已明确**：云同步、AWS SDK、账户体系均不在本项目范围。

### 2.4 法律与合规提示

逆向分析仅用于**产品功能对标与技术思路参考**，本项目的实现将**全部基于开源库自主开发**，不复制、不引用 Typora 的任何私有代码、资源文件或品牌标识。Typora 为商业软件，其代码与资源受版权保护。

## 3. 技术选型

### 3.1 核心技术栈

| 层 | 选型 | 理由 |
|----|------|------|
| **应用框架** | **Electron** | 天然「原生壳 + Web 渲染」架构，与 Typora 的架构理念一致；跨平台一致性强；生态最成熟；VSCode/旧版 Typora 同款方案 |
| **语言** | TypeScript | 类型安全，大型编辑器项目必备，重构与协作友好 |
| **前端框架** | React 18 | 组件化、生态大、与编辑器库集成方案多 |
| **构建工具** | Vite + electron-builder | 开发热更新快；electron-builder 成熟支持双平台打包 |
| **包管理** | pnpm | 速度快、节省磁盘、Monorepo 友好 |

### 3.2 关键依赖库（对齐 Typora 逆向发现）

| 能力 | 选型 | 说明 |
|------|------|------|
| **WYSIWYG 编辑内核** | **Milkdown** 或 **ProseMirror**（见 3.3 专门对比） | 所见即所得的核心 |
| **数学公式** | **KaTeX**（首选）/ MathJax 4 | 渲染快；KaTeX 体积更小更快 |
| **图表** | **Mermaid** + **ZenUML** | 与 Typora 对齐 |
| **代码高亮** | **Shiki**（首选）/ highlight.js | Shiki 用 VSCode 同款高亮，质量更高 |
| **文件搜索** | **ripgrep**（`@vscode/ripgrep` 或直接调用） | 与 Typora 一致，性能最优 |
| **Markdown 解析** | **remark** / **markdown-it** | 用于导出/预览管线 |
| **序列化** | **remark** + 自定义 serializer | 源码 ↔ DOM 互转 |

### 3.3 WYSIWYG 编辑器内核选型（重点决策）

这是本项目的核心决策，单独说明。

| 方案 | 原理 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| **A. Milkdown** | 基于 ProseMirror + remark，插件式 Markdown 编辑器框架 | 开箱即用；插件生态成熟；输入即 Markdown；源码↔WYSIWYG 双模式原生支持 | 相对较新，深度定制需理解其插件体系 | ⭐ **首选** |
| **B. 直接用 ProseMirror** | 底层编辑框架，需自行搭建 Markdown schema + 序列化 | 最灵活、可控性最高；Typora 级别的定制能力 | 开发量大，需自己写 schema/命令/序列化 | 备选（若 Milkdown 定制受限时降级） |
| **C. CodeMirror 6 + 装饰器模拟 WYSIWYG** | 用 CM6 的 decoration 隐藏语法符号、叠加样式 | 性能极佳、光标行为精确 | 实现「所见即所得」需要大量装饰器工作，且复杂块级元素（表格/嵌套列表）难做到位 | 不推荐用于 WYSIWYG，但源码模式可用 |

> **决策**：MVP 采用 **Milkdown**（方案 A），它本质就是 ProseMirror + remark 的 Markdown 专用封装，兼顾了开发效率与 Typora 级的 WYSIWYG 能力。若后续发现 Milkdown 无法满足某个深度定制点，再局部下沉到 ProseMirror（方案 B）直接操作，两者技术栈同源，迁移成本低。

### 3.4 为什么不用 Tauri（对比说明）

| 维度 | Electron | Tauri |
|------|----------|-------|
| 渲染一致性 | Chromium 固定版本，双端一致 | 依赖系统 WebView（macOS=Safari/WebKit，Windows=WebView2），渲染差异需逐个适配 |
| 编辑器生态兼容 | Milkdown/ProseMirror 等均在 Chromium 上充分测试 | WebKit/WebView2 对部分 CSS/JS 特性支持不一，WYSIWYG 编辑器风险高 |
| 内存/体积 | 较大（约 100MB+） | 小（约 10MB+） |
| 开发门槛 | 纯前端，低 | 需 Rust 基础 |

> 对于「WYSIWYG 编辑器」这种对渲染一致性要求极高的应用，**Electron 的 Chromium 固定版本是明确优势**，牺牲体积换稳定性是值得的。故最终选 Electron。

### 4.2 进程模型（Electron 标准三进程）

| 进程 | 职责 | 说明 |
|------|------|------|
| **主进程 (Main)** | 窗口生命周期、文件 I/O、原生 API、菜单、托盘、IPC 路由 | 仅一个 |
| **渲染进程 (Renderer)** | 编辑器 UI、渲染、交互 | 每个窗口一个，启用 `contextIsolation` + `sandbox` |
| **Utility/GPU 进程** | 由 Chromium 自动管理 | 无需干预 |

### 4.3 安全基线（Electron 必做）

- 开启 `contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`
- 渲染进程禁用 `remote`，所有原生能力通过 `contextBridge` 暴露的白名单 API
- 加载本地资源仅用 `file://` 或自定义协议，**不加载任何远程内容**
- `CSP` 限制 `script-src 'self'`，禁止内联远程脚本
- 图片等本地资源用 `webSecurity` 保持默认开启

### 4.4 数据流（编辑链路）

```
用户输入
   │
   ▼
Milkdown 编辑器（ProseMirror 状态）
   │  transaction 变更
   ▼
ProseMirror Doc (结构化 AST)
   │
   ├──▶ 实时渲染到 DOM（WYSIWYG）
   │
   └──▶ remark serializer ──▶ Markdown 文本
                                   │
                                   ▼
                         主进程写盘（防抖保存）
                                   │
                                   ▼
                         大纲/字数统计/预览导出
```

## 6. WYSIWYG 编辑器实现方案

### 6.1 核心机制：语法符号的「隐藏与显现」

Typora 的 WYSIWYG 本质是：**当光标不在某一行时，该行的 Markdown 语法符号（如 `#`、`*`、`**`）被 CSS 隐藏或样式化，只显示渲染效果；当光标移入该行时，语法符号重新显现以便编辑。**

在 Milkdown/ProseMirror 中的实现方式：

1. **AST 是唯一数据源**：Milkdown 内部用 ProseMirror 的 `Doc` 节点树，每个 Markdown 结构（标题、加粗、列表）对应一个 schema 节点，语法符号**不进入 DOM**（由插件在序列化时生成）。
2. **光标感知**：通过 ProseMirror 的 `Selection` 状态，判断光标当前所在节点。
3. **Mark 与装饰**：对「光标所在节点的语法符号」用 ProseMirror `Decoration` 渲染出临时的可见符号（如显示 `#`），非焦点区域则保持纯渲染样式。

### 6.2 关键交互能力清单

| 能力 | 实现要点 |
|------|----------|
| 输入 `#` + 空格 → 标题 | 监听输入，触发 Markdown 命令转换 |
| 输入 `- ` → 无序列表 | 同上，自动进入列表 |
| 输入 `**文本**` → 加粗 | Mark 的闭合触发 |
| 表格创建与行列编辑 | 自定义表格节点视图 + 行列工具栏 |
| 代码块 + 语言高亮 | 代码块节点视图 + Shiki |
| 数学公式（行内/块级） | `$...$` / `$$...$$` + KaTeX（**v1.1 引入**） |
| 图表（mermaid） | 围栏代码块 ` ```mermaid ` + Mermaid 渲染 |
| 任务列表 `- [ ]` | checkbox 自定义节点 |
| 图片粘贴/拖拽 | 主进程写入本地，渲染进程插入 |
| 链接自动识别与跳转 | 点击 + Cmd/Ctrl 跳转 |
| **中文输入法（IME）适配** | 见 6.4 节（**已确定：需专项适配**） |

### 6.3 中文输入法（IME）适配方案

中文拼音/五笔等输入法使用「组合输入（Composition）」机制，与 WYSIWYG 的「输入即转换」存在天然冲突：组合中的拼音字母不应触发 Markdown 语法转换。需专项处理：

| 场景 | 问题 | 处理方案 |
|------|------|----------|
| 拼音组合中 | 组合中的字母被误判为 Markdown 符号（如 `#`、`*`） | 监听 `compositionstart` / `compositionend`，组合期间**暂停所有 Markdown 自动转换** |
| 候选词上屏 | 上屏时触发多余的事务 | 仅在 `compositionend` 后统一应用一次事务 |
| 半角/全角符号 | 中文输入法切换全角符号 | 对全角符号做归一化判断（可选，低优先级） |
| 光标与装饰符 | 组合期间装饰符位置错乱 | 组合期间冻结 decoration 重算 |

> **实现要点**：在 Milkdown 的 input 规则与键盘事件处理中，增加一个「IME 组合状态守卫」。ProseMirror 已内置 `compositionstart/end` 事件支持，但需在自定义 Markdown 转换命令处显式跳过组合状态。这是国内用户体验的关键点，M1 阶段即需纳入，而非事后修补。

### 6.4 大文档性能策略

- **虚拟化渲染**：仅渲染可视区域 + 缓冲区（Milkdown 社区有成熟方案，或 ProseMirror 的 `Decoration` 惰性计算）
- **防抖序列化**：源码持久化用 500ms 防抖
- **分块解析**：超大文件（> 5MB）降级为「纯文本模式 + 折叠预览」
- **Math/图表懒渲染**：非可视区域的公式与图表延迟渲染

## 7. Markdown 解析与渲染管线

### 7.1 双管线设计

| 管线 | 用途 | 技术 |
|------|------|------|
| **编辑管线** | WYSIWYG 编辑，AST 即 ProseMirror Doc | Milkdown（内部 remark 解析） |
| **导出/预览管线** | 生成 HTML/PDF、纯预览 | remark-rehype → HTML |

两条管线**共享同一套 remark 插件**（GFM、脚注、数学、表格等），保证编辑所见与导出结果一致。

### 7.2 支持的语法范围（对齐 Typora 核心）

- **块级**：标题（1-6）、段落、引用、有序/无序列表、任务列表、表格、代码块、分割线、脚注、数学块（v1.1）
- **行内**：加粗、斜体、删除线、行内代码、链接、图片、行内数学（v1.1）、高亮标记、上下标
- **扩展**：GFM（GitHub Flavored Markdown）、目录 TOC、YAML front matter（可选）
- **图表**：Mermaid（流程图/时序图/甘特图/类图等）、ZenUML 时序图

### 7.3 导出

| 目标格式 | 实现 |
|----------|------|
| HTML | remark-rehype + 主题 CSS 内联 |
| PDF | 复用 HTML + Electron `webContents.printToPDF` |
| 图片 | 可选（HTML → 截图，低优先级） |

## 8. 文件管理

### 8.1 职责划分

- **主进程**负责所有文件 I/O（读写、监听、最近文件记录）。
- **渲染进程**通过 IPC 调用，不直接碰文件系统（安全基线要求）。

### 8.2 关键能力

| 能力 | 实现 |
|------|------|
| 打开文件 | 系统对话框 / 拖拽 / 命令行参数 |
| 保存 | 防抖自动保存（默认 500ms）+ `Cmd/Ctrl+S` 手动保存 |
| 自动保存 | 主进程 `fs.writeFile` + 原子写入（先写临时文件再 rename） |
| 外部修改监听 | `fs.watch` 检测外部变更，提示重新加载 |
| 最近文件 | 主进程持久化 JSON（`userData` 目录） |
| 编码识别 | 自动检测 UTF-8 / GBK 等（用 `jschardet`） |
| 换行符 | 尊重文件原有 CRLF/LF |
| 图片粘贴 | **默认存相对路径 `assets/` 目录**（与文档同级的 `assets` 文件夹，引用 `assets/xxx.png` 相对路径） |

> **图片粘贴存储策略（已确定）**：粘贴/拖入的图片默认保存到当前文档同级目录下的 `assets/` 文件夹，Markdown 中使用相对路径 `![name](assets/xxx.png)` 引用。保证文档可移植（整个目录拷走即可用）、避免 `.md` 文件体积膨胀。

### 8.3 配置存储

- 应用配置（主题、字体、快捷键）→ 主进程 `userData/config.json`
- 使用 `electron-store`（或自研 JSON 封装）

## 9. 主题系统

### 9.1 设计（对齐 Typora 的「主题 = CSS」模型）

- **主题即一份 CSS**，通过 CSS 变量定义颜色/字体/间距。
- 内置主题（MVP 先做 3 套）：
  - `light`（明亮，默认）
  - `dark`（深色）
  - `github`（GitHub 风格）
- 主题文件结构：`packages/theme/themes/<name>/theme.css`
- 支持用户自定义主题（放到 `userData/themes/`，应用启动扫描加载）。

### 9.2 CSS 变量规范（示例）

```css
:root {
  --md-font-size: 16px;
  --md-line-height: 1.6;
  --md-text-color: #333;
  --md-bg-color: #fff;
  --md-heading-color: #000;
  --md-link-color: #4183c4;
  --md-code-bg: #f5f5f5;
  --md-border-color: #ddd;
  /* ... */
}
```

编辑器与预览/导出共用同一套变量，保证「编辑所见 = 导出所得」。

## 12. 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| **WYSIWYG 复杂度高** | 核心体验难达标，开发周期长 | 用 Milkdown 降低门槛；先做「Typora 同款核心 80% 语法」；必要时下沉 ProseMirror |
| **Milkdown 深度定制受限** | 某些细节无法 100% 复刻 Typora | 明确「对标而非复刻」；受限点局部用 ProseMirror 插件补 |
| **大文件性能** | 万行文件卡顿 | 虚拟化渲染 + 分块解析 + 超限降级纯文本 |
| **跨平台渲染差异** | Windows 字体/DPI 显示差异 | Electron 固定 Chromium 已大幅消除；字体用 fallback 链；DPI 用 `devicePixelRatio` 适配 |
| **图片粘贴的存储策略** | 图片路径引用混乱 | 已确定：仅存相对路径 `assets/` 目录，统一处理（见 8.2 节） |
| **Electron 包体积大** | 分发体积约 100MB+ | 接受；后续可评估 pnpm + 精简依赖优化 |
